Asunto: QA Sis2000 — tabla intermedia de cambios de póliza hacia RMS (sin cron de 1–5 minutos)

Buenos días,

Les proponemos una tabla intermedia en Sis2000 QA para registrar cada modificación de póliza (personas, coberturas, vigencia, estatus) y sincronizarla con RMS sin un job agresivo.

Hoy un cron de 1 o 5 minutos tendría que preguntarle a Sis2000, una y otra vez, si cambió algo en adpoliza / adpolcob / maclient. Eso barre tablas grandes, carga el servidor y igual se puede perder un cambio si fultmod no se actualiza.

Con este diseño no se consulta el inventario cada minuto. El cambio se anota en el momento en que se graba: queda el registro en la tabla intermedia (qué póliza, cuándo, el snapshot). Después se lee solo esa cola, cuando convenga:

- al sincronizar desde RMS
- desde una pantalla / visual de Sis2000 o SysIP (“enviar pendientes”)
- o un cron amigable, de mucho más intervalo (por ejemplo cada hora o al cierre), que solo hace SELECT de filas PENDIENTE, no un barrido de coberturas

Adjunto el script: sp_encola_poliza_rms_nexus.sql

No incluye trigger ni llamada HTTP. SQL Server 2019 no dispara HTTP desde el SP; el SP solo deja el cambio en la tabla. Nuestro servidor (o la visual / el job largo) lee PENDIENTE, envía a RMS y marca MIGRADO. El histórico de la modificación se queda en esa misma tabla.


1) Qué crear (solo estos objetos)

- Tabla dbo.sync_poliza_evento_rms_nexus   registro de lo modificado (buzón + bitácora)
- SP dbo.sp_encola_poliza_rms_nexus        lo ejecutan ustedes al grabar
- SP dbo.sp_sync_poliza_pendientes_rms_nexus   lectura de PENDIENTE
- SP dbo.sp_sync_poliza_marcar_rms_nexus       pasa a MIGRADO / ERROR

Publicar en Sis2000 QA (la misma base de NAME_BD de nest-api, normalmente sis2000_qa), en SSMS. Si usan Azure Data Studio, no pegar la palabra GO (ejecutar lote por lote).


2) Por qué esta tabla y no un cron corto

- El cron de 1–5 min pregunta “¿cambió algo?” a todo el núcleo. Esta tabla responde “esto cambió”, porque el SP lo escribió al editar.
- No se recorre adpolcob ni adpoliza en cada ciclo. Se leen 10–20 filas PENDIENTE.
- Queda constancia: cnpoliza, fecha, origen, payload (personas + coberturas) y el estado (PENDIENTE / MIGRADO / ERROR).
- Si RMS o la red fallan, la fila sigue PENDIENTE. No se pierde el cambio.
- La lectura puede ser bajo demanda (RMS o visual Sis2000) o un job de intervalo largo. No hace falta cada minuto.


3) Cómo se llena (al editar la póliza)

Cada vez que se edite en Sis2000 —personas, coberturas, vigencia, estatus, tomador/asegurado/beneficiario— al confirmar el grabado:

  EXEC dbo.sp_encola_poliza_rms_nexus
      @cnpoliza = N'<cnpoliza>',
      @fanopol  = <año>,
      @fmespol  = <mes>,
      @origen   = N'SP';

El SP arma un JSON con la póliza completa (cabecera + personas + coberturas de adpolcob del último recibo vigente) y deja o actualiza una fila PENDIENTE. Si ya había PENDIENTE de esa póliza, refresca el snapshot (no duplica).

Enganchar el EXEC al final de:

- Endoso de datos de personas
- Cambio de coberturas (adpolcob)
- Cambio de vigencia o estatus (adpoliza)
- Emisión / renovación

Mismo SP en todos los casos. El snapshot sale completo, no un campo suelto. No enviar marca ni vehículo. No activar triggers sobre adpoliza / maclient / adpolcob.


4) Cómo se vacía (sin cron agresivo)

Quien lea la cola (nuestro nest-api POST /api/rms-sync/drenar, una visual en Sis2000, o un job de intervalo largo):

  PENDIENTE  →  MIGRADO     RMS ya recibió el snapshot; el registro se conserva
  PENDIENTE  →  PENDIENTE   si RMS falla; se reintenta; sube intentos
  ERROR                     solo si hay que sacarlo de la cola (motivo en xerror)

La tabla no se borra al migrar: queda el historial de que esa póliza se modificó y cuándo se homologó.


5) Prueba en QA

DECLARE @pSuccess BIT, @pErrorMessage NVARCHAR(MAX);

EXEC dbo.sp_encola_poliza_rms_nexus
    @cnpoliza      = N'7-1-1000002371',
    @fanopol       = 2026,
    @fmespol       = 9,
    @origen        = N'SP',
    @pSuccess      = @pSuccess OUTPUT,
    @pErrorMessage = @pErrorMessage OUTPUT;

SELECT @pSuccess AS pSuccess, @pErrorMessage AS pErrorMessage;

SELECT TOP 5
    id, cnpoliza, fanopol, fmespol, origen, estado, intentos, fcreated
FROM dbo.sync_poliza_evento_rms_nexus
ORDER BY id DESC;

Debe salir una fila PENDIENTE. El payload_json debe traer poliza_detalle.poliza, poliza_detalle.riesgo y poliza_detalle.Coberturas.

Ajustar cnpoliza / fanopol / fmespol a una póliza real de esa base.


6) Estados

  PENDIENTE  el cambio quedó registrado; aún no se envió a RMS
  MIGRADO    ya se homologó con RMS (el registro sigue en la tabla)
  ERROR      no reintentar en automático (detalle en xerror)

Quien escribe PENDIENTE: el SP de ustedes, en el grabado.
Quien pasa a MIGRADO: la sincronización (RMS, visual Sis2000 o cron largo), no un barrido cada minuto.


7) Qué no hacer

- No crear trigger sobre adpoliza, maclient ni adpolcob
- No llamar HTTP / RMS / nest desde el SP
- No montar un job de 1 o 5 minutos recorriendo adpolcob / adpoliza
- No publicar esto en Sis2000_DES si nest-api apunta a otra base (NAME_BD)

Cualquier duda sobre el script, lo vemos juntos antes de engancharlo en SysIP.
